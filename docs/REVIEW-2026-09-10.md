## 4. RV-01：モダン可の判定不一致

### 根拠と影響

- [derive.ts](../src/lib/graph/derive.ts) の `flattenCombo()` は、いずれかのstepで `stepModernCommand()` が値を返すと `usesModern = true` にする。
- [ComboCard.astro](../src/components/ComboCard.astro) は `flat.usesModern` で「モダン可」を表示する。
- [ComboExplorer.astro](../src/components/ComboExplorer.astro) は同じ値から `data-modern` を作り、絞り込みに使う。
- [コンボ詳細](../src/pages/manon/combos/[slug].astro) は `comboSupportsModern()` を使い、本線の全Routeが `controlType: 'both'` の場合だけモダンを有効にする。

「モダン入力を持つ手がある」と「コンボ全体がモダンで実行できる」は別の意味。現在はこの違いが一覧と詳細の矛盾になる。

再現対象は `manon-punish-5hp-rondpoint`。本線に `controlType: 'classic'` の `route_pc_5hp_rondpoint` を含む一方、別のstepにモダン入力があるため一覧側の判定がtrueになる。これはダミーの技割り当ての正誤とは独立した論理不具合。

### 最小修正案

1. 対応可否の判定元を既存の `comboSupportsModern(combo)` に統一する。
2. `FlatCombo.usesModern` を `supportsModern: boolean` に置き換える。単なる改名ではなく、算出ロジックも変更する。
3. `flattenCombo()` 内の `let usesModern` とstep単位のtrue代入を削除し、返却時に `supportsModern: comboSupportsModern(combo)` を設定する。
4. カードと一覧フィルタを `flat.supportsModern` に変更する。詳細も同じ関数の結果を使い、別の条件式を追加しない。
5. `rg` で `usesModern` の残存参照を確認する。もし別用途に残すなら `hasModernCommand` 等の意味の明確な名前にし、対応可否には利用しない。
6. 空のrouteChainが `every()` の空集合評価によって対応可にならないよう、共通関数でも `routeChain.length > 0` を条件に加える。空chainはデータ検証でもエラーにする。

概念上の返却変更:

```ts
return {
  // 既存の他フィールド
  supportsModern: comboSupportsModern(combo),
};
```

この修正は「記録されたRoute対応可否を全画面で一貫して使う」もの。入力内容がゲーム内で正しいことまで保証するものではなく、その課題はRV-02で扱う。

### 完了条件・回帰確認

| ケース | 一覧バッジ | モダン可フィルタ | 詳細モダン切替 |
|---|---|---|---|
| 本線にclassic限定Routeあり、一部stepにはモダン入力あり | 出ない | 除外 | 無効 |
| 本線の全Routeがboth、入力も整備済み | 出る | 含む | 有効 |
| 本線はboth、別の締め・起き攻め分岐だけclassic限定 | 出る | 含む | 有効。モダングラフから該当分岐だけ除外 |
| 空のrouteChain | 公開しない | 公開しない | 検証エラー。判定関数単体でもfalse |

- `manon-punish-5hp-rondpoint` が最初のケースを満たす。
- 全コンボについて一覧・フィルタ・詳細の結果が一致する。
- 条件付きURLをリロードしても同じ結果になる。
- 回帰テストでは「一部stepに入力あり、ただし本線はclassic限定」を必ず含める。関数の戻り値だけでなく、カード・フィルタへの配線も確認する。
- ビルドと型チェックを通す。RV-01のPRに大規模なスキーマ変更を混ぜない。

## 5. RV-02：モダン入力の確実性と手動入力

### 根拠

[types.ts](../src/data/types.ts) は `inputModern: null` をモダンに存在しない技と説明している。一方、ダミーデータにはnullと `inputModernPrecise` の併存がある。現行の [入力解決](../src/data/index.ts) は `inputModernPrecise` を参照せず、解決できない入力は [Sequence](../src/components/notation/Sequence.astro) と [Notation](../src/components/islands/Notation.tsx) で `deriveModern()` にフォールバックする。

### 修正案

- 入力解決結果に `verified / unverified / unsupported` 等の状態を持たせる。
- 確認済みの場合に簡易入力・手動入力の選択肢を持たせ、どの入力をそのstepで使用するか明示する。
- 表記の明示指定だけで「確認済み」にはしない。確認状態も必要。
- `unsupported` は推定変換しない。`unverified` は未確認と表示し、本番のモダン可認定には使わない。
- `deriveModern()` は編集時の候補生成に限定する案を推奨。プロトタイプで残す場合も、推定と確定を識別する。
- DR・ダッシュ・待ちなどの共通操作は、技辞典の欠落と区別する。非技操作に一律でmoveKeyを要求しない。
- Routeの対応宣言と、各stepの使用可能な入力が矛盾したら検証で指摘する。
- モダン専用コンボを初回対象に含めるか決める。含める場合、現行の `'classic' | 'both'` では表現できないため、グラフのclassic側フィルタも含めて拡張する。

完了条件: 非対応・未確認を架空の入力で埋めない。手動入力だけで可能な技を正しく表現できる。AstroとPreactの表示結果が一致する。ダメージの確認条件とも入力方式が一致する。

P2-10の推定精度改善自体は低優先のままでよいが、未確認情報を確定表示しない対応は公開前に行う。

## 6. RV-03：共有ノードと接続の成立条件

### 根拠

[flow.ts](../src/lib/graph/flow.ts) は同一Situationの出辺を展開するが、`Route.constraints` は評価しない。型の連続性検証も基本はfrom/toのID一致。自由記述の条件は主にパーツ詳細に表示される。

### 修正案

1. P2-4を二段階に分け、移行前のTS形式で代表的な実例を登録する。
2. 中央／端、通常始動／条件付き始動、共通の締め、受け身別の起き攻め、classic限定／両対応などを含める。件数だけでなく条件の種類を優先する。
3. 共有するノードについて「各到達経路 × 後続Route」の接続表を作り、成立・条件付き・未確認を記録する。
4. 後続の成立条件が一致しないなら、初期実装ではSituationを分割する。高度な条件評価器は必須にしない。
5. 条件付き接続を残す場合、条件をグラフとカードにも表示する。`constraints` の全文を常に押し込むのでなく、必須条件の短い表示を持つ。
6. 型の整合性とゲーム内の成立確認を別々に管理する。IDがつながるだけで検証済みにしない。

完了条件: 公開グラフに、未確認の連結が無条件の成立ルートとして現れない。ノード分割／共有の判断例をP2-5のCONTENT.mdに掲載する。ループ・既出・深さ打ち切り後にも参照先があり、同じ状況に到達した際の情報省略が誤解を生まない。

## 7. RV-04：ダメージと測定条件

### 根拠

`flattenCombo()` は `Route.damage` を合算し、`damageOverride` があれば上書きする。仕様は補正・メダル・入力方式による違いを想定しているが、合計値の確認条件を構造化していない。初期ソートはダメージ順。

### 修正案

- コンボ単位の測定結果として「合計ダメージ・確認条件・確認状態・確認バージョン」を保持する。
- 条件は実例から必要項目を決める。候補は操作方式、入力方式、メダル、ヒット条件、必要な相手状態・位置。
- 初期公開では測定済みの値を優先し、未確認値は非表示または明確な目安表示にする。
- 既存 `damageOverride` から段階移行できる。旧ダミーの上書き値を自動的に確認済み扱いにはしない。
- モダン切替時に数値が変わる場合は対応する測定結果を表示する。結果がなければ未確認と表示する。あるいは数値がどの固定条件の値か明示する。
- 異なる条件の数値を無条件に比較しない。ダメージソートの対象条件と未確認値の配置を決める。
- Routeの単体目安を残す場合は、コンボ全体の実測値とラベルを区別する。

完了条件: 数値の確認条件を詳細画面から読み取れる。共有パーツを別の経路から使っても、単純合算値が実測値として表示されない。未確認を0ダメージとして扱わない。

## 8. RV-05：モバイル・練習時の導線・キーボード

### 確認した構造

- コンボ詳細は高さ860pxのグラフが先で、レシピは下の折りたたみ。
- 状況詳細のグラフは高さ800px。
- [FlowCanvas](../src/components/islands/FlowCanvas.tsx) は `touch-action:none`、wheelで `preventDefault()` してズームする。
- [マノンハブ](../src/pages/manon/index.astro) のタブはradioを `display:none` にし、labelにキーボード操作を実装していない。

### 修正・検証案

- 詳細の上部に短いレシピを置き、コピー操作を追加する案を比較する。グラフは分岐理解のために維持する。
- 通常表示ではページスクロールを優先し、「グラフを操作」や全画面でパン・ズームを有効化する案を実機で試す。
- 高さは画面サイズに応じた値にする。操作領域に入っても上下の本文へ移動できることを確認する。
- 起き攻めは直近の択を先に比較し、後続は選択展開する案を現行再帰表示と比較する。これは採用未定のUX仮説。
- タブは標準のbutton／リンクによる構造へ変更する。タブ方式なら選択状態、関連パネル、矢印キーによる移動を実装する。別URL方式なら通常リンクでよい。
- グラフ全画面はフォーカス移動・復帰、背景操作抑制、Esc終了を確認する。切替ボタンの選択状態を支援技術にも伝える。
- 固定最小幅のグリッドを含め、320／375／390px程度の幅でページ全体の横はみ出しを確認する。グラフ内部やレシピの意図的な横移動とは区別する。

完了条件: スマートフォンとキーボードで、コンボ検索→レシピ確認→起き攻め選択が完了できる。スクロールがグラフ操作に奪われ続けない。JavaScriptの読み込み失敗時も静的レシピ・リンクから必要情報にアクセスできる。

想定利用者3〜5人程度に上記課題を実施してもらい、完遂可否・迷った箇所・拡大操作の頻度を記録する案を推奨。人数や合格基準は運用規模に合わせて設定する。

## 9. RV-06：検索項目とフレーム表示の意味

### 始動検索

[ComboExplorer](../src/components/ComboExplorer.astro) の「始動」は始動技ではなく `start.kind` を使う。現在のコンボはneutral始点に集まり、2中K／5中Pなどの検索を十分に表現できない。

修正案:

- `starterMoveKey` 等の検索用項目を持たせるか、先頭Routeの始動技を共通関数で解決する。
- 先頭が操作stepの場合のルールを決め、単純に最初のcommand文字列で分類しない。
- UI表記を「始動技」にし、2中K等で絞り込めるようにする。
- 所持ゲージ以内の検索、目的（起き攻め重視・メダル重視・倒し切り）、最初に覚える候補は追加検討。初回公開に必要なものを実利用で選ぶ。
- `anywhere` を中央／端の検索に含めるか、ゲージの「消費合計」と「始動時に必要な量」をどう区別するかを仕様に書く。
- フィルタとタブのURL共有・戻る操作の期待動作を決める。現在のフィルタ同期だけで全状態の復元ができるとはみなさない。

### 有利フレーム

`RouteProperties.frameAdvantage` は、重ねた後の有利と前ステ・微歩き後の有利を含む。画面では「初回行動後」と一括表示するため比較対象が曖昧。

修正案:

- 「重ねをガードされた後」「前ステップ後、相手の起き上がりまで」等の測定対象を区別する。
- 数値化する場合は `frames: number` と測定対象・条件・補足を分け、`+`や`F`は表示時に付ける。近似値は近似と分かる属性か注記を付ける。
- 受け身別の値と代表値の関係を決める。どちらの受け身の数値か表示する。
- ガード後の値と残り猶予を同じ意味として並べ替え・色判定しない。

完了条件: 始動技で探した結果が意図したコンボになる。フレームの数値が何と何の差か、グラフまたは隣接する説明から判断できる。

## 10. RV-07：確認状態とパッチ追随

現状の `verifiedVersion` はMoveにある。技辞典の確認と、コンボ・起き攻めの成立確認は別の作業。

修正案:

- Route／Comboにも確認バージョン・確認日・出典・状態を持たせる。例: `unverified / verified / needs_recheck`。状態名は提案。
- 技更新時、`moveKey → Route → Combo` の逆引きで影響候補を出す。起き攻めや到達Situationへの影響も確認対象に含める。
- 共有Routeが変わったとき、既存Comboの確認記録をそのまま最新扱いにしない。依存情報の版・変更検知のルールを決める。
- 更新手順は「変更候補抽出→影響一覧→再確認→公開更新」としてCONTENT.mdに記載する。
- 誤りの報告入口を設け、対象URL・確認バージョン・再現条件を受け取れるようにする。

完了条件: 未確認／旧版の情報を利用者が識別できる。技またはRouteの変更から再確認対象を抽出できる。

## 11. RV-08：検証コマンドとビルドゲート

### 実行結果（2026-09-10のレビュー時）

| コマンド | 結果 |
|---|---|
| `npm run build` | 成功。45ページ生成 |
| `npm run astro -- check` | 39ファイル、エラー・警告・ヒントすべて0 |
| `node scripts/validate.mjs` | 失敗。Node v24.16.0で `ERR_UNSUPPORTED_DIR_IMPORT` |

最初のビルドはサンドボックスの `spawn EPERM` で失敗したが、承認された制限外実行で成功した。これはアプリのビルド不具合とは区別する。

### 修正案

- [validate.mjs](../scripts/validate.mjs) が読み込むTSのディレクトリimportは、NodeのESM実行で解決できない。型チェック成功だけではCLIの動作を保証しない。
- 例えばTS実行用ランナーを導入して `npm run validate` に集約する、または検証コードをNodeで実行可能な形式へビルドする。選択した方式でWindowsとCIの両方を確認する。
- 現行のトップページ内の警告出力から、公開ビルド開始時に実行し失敗を伝播する仕組みに移す。Collections導入後は同じcontentデータを検証する。
- ID重複、参照先欠落、空steps／空chain、chain連続性、キャラ不一致、対応宣言と入力の矛盾を検証対象にする。
- Map化する前に重複を検出する。現在のMapは重複キーを上書きしてしまう。
- 孤立ノードは公開レコードと下書きを分けて扱う。下書きの未接続まで一律に公開ビルドを妨げる設計にはしない。
- graphのループ／既出／深さ上限、入力パーサ、モダン判定の回帰テストを優先する。

完了条件: 文書化した単一の検証コマンドが成功する。不正データの代表ケースを注入したテストで失敗終了を確認する。公開ビルドが検証失敗を無視しない。

## 12. RV-09：ロードマップ変更案

### 評価

現行は作業分解と依存関係が整理されている。一方、担当・実工数・稼働時間・初回公開対象・完了条件が不足し、納期を判断できるスケジュールにはまだなっていない。

| 既存項目 | 推奨変更 |
|---|---|
| P2-1／P2-2 | RV-01は先に修正。代表実例の検証後に必要な型変更と移行を行う |
| P2-3 | RV-08を組み込み、CLI修正は移行前でも着手する |
| P2-4 | 前半: 現行TSで代表実例を検証。後半: 移行先へ正式シードを登録 |
| P2-5 | 命名・ノード共有基準の草案を先に作る。実例検証後に確定する |
| P2-6 | 最初はテキスト入力・正規化・既存パーツ候補・差分プレビュー・確認後反映に絞る。画像／動画解析は後続 |
| P2-7 | 「全技・全コンボ」を初回公開の具体的な掲載一覧へ変更。Skillに依存せず手入力でも進められるようにする |

| P2-11 | 実データ・UI・検証・環境をまとめた公開ゲートを追加 |
| C-1.5 | 共有プレビューは早期に用意する。ダミー公開範囲と検索対象への混入を考慮し、本番と区別する |

Content Collectionsへの移行を「TS配列をJSONへ変えるだけ」と見積もらない。非同期取得、contentのIDと業務ID、参照解決、既存URLの維持、下書き除外、検証実行タイミングを含める。取得後に索引を作って既存の同期導出関数へ渡す境界を設けると、変更範囲を抑えやすい。

参考: [Astro Content Collections公式ガイド](https://docs.astro.build/en/guides/content-collections/)（レビュー時参照）。実装時はプロジェクトの導入バージョンに合わせて確認する。

### 推奨する実施順とゲート

| 順序 | 作業 | 完了条件 |
|---|---|---|
| 1 | RV-01の独立修正と回帰確認 | 一覧・フィルタ・詳細の対応可否が一致 |
| 2 | 初回公開対象と代表実例を選定 | オーナーの確認対象と入力担当が明確 |
| 3 | 現行TSで実例検証、RV-02〜04の型方針を決定 | 接続・数値・入力の不足と対応方針が記録済み |
| 4 | 型修正、Collections移行、検証と重要テスト | 公開データの不整合でビルド失敗、既存URL維持 |
| 5 | 限定データ整備、RV-05〜07、基本SEO | 主要操作と更新手順を確認済み |
| 6 | プレビューで公開ゲート確認、本番公開 | 下記チェックを満たす |
| 7 | 登録支援とデータ拡大 | 手入力で判明した反復作業を自動化 |

依存しない作業は実データ確認待ちの間に進められる。たとえば検証CLI修正・タブ操作修正・プレビュー環境整備。ただし、ゲーム内確認をAIによるデータ推定で代替しない。

### スケジュール化するときに追加する列

各タスクに「担当」「見積実工数」「依存」「完了条件」「予定期間」「確認待ち時間」「実績」を追加する。まず代表実例1本の登録・確認時間とRV-01の実績から残件を見積もる。開発実工数とオーナーのゲーム内確認・判断待ちを分離する。稼働時間が不明な現段階では固定の公開日を置かない。

### 初回公開ゲート案

- [ ] 公開対象のコンボ・起き攻めが具体的に列挙されている。

- [ ] 一覧・フィルタ・詳細で対応可否が一致する。
- [ ] ダミー・下書き・開発プレビューが本番掲載対象から除外される。

## 13. Claudeへの引き継ぎ要約

1. 最初にRV-01を独立して修正する。オーナーが重要性を明示した確認済み不具合であり、Collections移行を待つ理由はない。
2. 本資料の提案を現行仕様と照合し、採用する項目をSPEC.mdとROADMAP.mdへ反映する。採用未定のUX案を確定事項として転記しない。
3. ダミーの具体的な技・数値は正解扱いにしない。既存データは表示ロジックの回帰検証、実データはゲーム内容の検証に使い分ける。
4. 少数の実例でスキーマを検証し、その結果で型・公開範囲・工数を調整する。
5. 作業報告には修正したID、変更内容、確認結果、残課題を記載する。本資料を作成したこと自体を、指摘の修正完了として扱わない。
