# 公開後の第三者レビュー — 2026-09-12

Claude に修正を引き継ぐための資料。アプリケーションの実装変更・データ修正・デプロイは実施していない。

## 1. 評価の結論と対象

**コンボから起き攻めへつながる構造、データと描画の分離、静的配信を中心とする構成はよい。全面的な作り直しより、データの意味を画面まで正しく届ける修正と、スマートフォンでの閲覧改善を優先したい。**

とくに、モダンの精密入力を登録しても画面で別の入力に変換される問題、空振り・フェイントが一覧で省略される問題、セットプレイの入口から一部データが見つからない問題は、ツールの信頼性に直接影響する。型検査・ビルド・既存テストが通ることと、利用者に正しい内容が届くことの間に検証の穴がある。

デザインはレトロなゲーム風の意図が伝わり、ダーク／ライトの方向性も一貫している。「モダンでないから全面刷新すべき」とは評価しない。ただし、情報の優先順位、文字の読みやすさ、スマートフォンの画面占有、キーボード操作は改善が必要。

| 観点 | 評価 |
| --- | --- |
| 企画・情報モデル | コンボの終点から次の選択肢へ進める点が強み。確定コンボ・読み合い・状況の意味の整理が次の課題 |
| 実装構成 | Astro + Preact の部分的な対話機能は用途に合っている。現規模で大規模な構成変更をする理由は薄い |
| 表示の信頼性 | 入力方式と行動種別の解決に不整合があり、優先修正が必要 |
| 探しやすさ | フィルターは豊富だが、最初の候補を見るまでが長い。セットプレイ抽出も統一されていない |
| 見た目・操作 | 世界観は維持できる。モバイル配置、文字階層、コントラスト、全画面操作を改善したい |
| AI 開発の品質管理 | スキーマとテストの基礎はある。実データを通した表示検証、ドラフト反映前の検証、公開ゲートが不足 |

### R01 — 精密入力があるのに別のモダン入力を生成する

対象：[入力解決](../src/data/index.ts)、[可否検証と集計](../src/lib/graph/derive.ts)、[Sequence](../src/components/notation/Sequence.astro)。

`stepModernCommand()`（96 行付近）の優先順位は `step.commandModern` → `move.inputModern` → 未定義。`inputModernPrecise` を参照しない。一方、可否の検証は `inputModernPrecise` があれば両対応を許容する。このため「モダン可」は正しくても、表示が機械的な変換に戻る。

再現：`/manon/combos/manon-mid-lp-degage/` を開いてモダン表示にする。`manon-degage-l` には `inputModern: null`、`inputModernPrecise: "214L"` が登録されているが、グラフは **`214SP`** を表示する。グランフェッテ系でも精密入力が無視されるデータがある。

修正方針：

1. 可否とコマンドを同一の resolver から返す。返り値には `available`、`command`、`inputMethod`、`source`、`reason` などを持たせる。
2. 明示入力を優先し、簡易入力が存在しない場合は登録済み精密入力を使う。簡易／精密の選択で技の強度や条件が変わる場合は、辞典の代表入力だけで判断せず Step に選択を記録する。
3. ゲーム上の正しさを保証できない汎用変換を、公開用の入力の暗黙フォールバックにしない。未解決は検証エラーか「入力未確認」とする。
4. カード・グラフ・テキスト・フィルターが同じ解決結果を使う。

完了条件：上記実データで `214L` が表示される。明示指定、簡易入力、精密入力のみ、非対応、未解決の各ケースをテストし、対応可否と各画面の表示が一致する。

### R02 — 行動種別が一覧とグラフで欠落する

対象：[ComboCard](../src/components/ComboCard.astro) 33 行付近、[FlowCanvas](../src/components/islands/FlowCanvas.tsx) 56 / 569 行付近、[共通 UI 辞書](../src/lib/ui.ts)。

カードは `Sequence` に command だけを渡すため、`Step.action` の空振り・フェイントや注記を表示しない。補正切りセットプレイに含まれる「空振りする操作」が、通常の攻撃を当てるレシピに見える。また FlowCanvas 独自の `STEP_ACTION_TAG: Record<string, string>` には `feint` がなく、共通辞書に追加済みでもグラフのバッジが空になる。

修正：入力表記だけの部品と、行動を含むレシピ表示部品を区別し、カード・詳細は共通の action 対応部品を使用する。辞書は `Record<StepAction, ...>` などで網羅性を検査する。省略表示でも「空振り」「フェイント」は残す。保証された連続ヒットと、その後の読み合いを接続記号・ラベルで区別する。

完了条件：補正切りコンボを一覧だけで見ても必要な空振り／フェイントが分かる。新しい action を追加して表示辞書が未対応なら型検査かテストが失敗する。

### R03 — フレーム・状態・報酬の意味を同じ欄で扱っている

対象：[FlowCanvas](../src/components/islands/FlowCanvas.tsx) 596 行付近、[Situation スキーマ](../src/data/schema.ts)。

`Situation.advantage` を一律「相手復帰まで {advantage}」としている。実際に `kd_after_manege_dore_mid` 等では **「相手復帰まで メダル獲得 +1」** と表示される。別の状況には「前ステ後 +3」が入っており、状況成立直後の余裕と、行動後の有利フレームが混在する。

修正：報酬（メダル）、相手状態、自由記述、数値フレームを分ける。フレームは値だけでなく基準イベント、ヒット／ガード、行動・受け身などの測定条件を保持する。「初回行動後」も実際にその条件で測ったものにだけ使う。既存の曖昧な文は notes に移し、数値を推測で補わない。

完了条件：「メダル獲得」が復帰時間として出ない。同じ `+3` でも何の後の値か表示から判断できる。

### R04 — セットプレイの入口にデータが出てこない

対象：[トップ](../src/pages/index.astro) 7 行付近、[キャラクターページ](../src/pages/[character]/index.astro) 23 行付近。

トップは `起き攻め開始` タグ、キャラクターページは kind の制限と outgoing okizeme、状況詳細は outgoing okizeme で判断する。実データでは okizeme の出る状況が 9 件あるのに、キャラクターの一覧対象は 6 件、トップの対象は 4 件。

`blanka_sa2_active_mid`、`kd_after_hoseigiri_corner`、`kd_after_hoseigiri_feint_mid` は `kind: hit` のためキャラクターのセットプレイ入口から漏れる。状況詳細には遷移できるので「データが存在しない」問題ではない。

修正：`getSetplayStarts(character)` のような共通問い合わせを用意し、表示対象の役割を明示する。起き攻め以外の連係も掲載するなら UI 名称も「セットプレイ・連係」等に合わせる。トップに抜粋する意図があるなら「全件数」と「おすすめ掲載数」を区別する。

完了条件：対象を一つ追加した際、入口・件数・詳細の整合がテストで保証される。上の 3 件の採否を明示的に判断する。

### R05 — 数値の確からしさと、どこまでのダメージかを表示する

対象：[集計](../src/lib/graph/derive.ts)、[ComboCard](../src/components/ComboCard.astro)、コンボ・パーツ JSON。

補正式の未実装とは別に、次の意味の不一致がある。

- `blanka-antiair-5mk-electric` のパーツは「基礎値合計・補正未反映・実測待ち」と注記されているが、コンボに `damageNote` がないため一覧と詳細では 2,200 が通常の数値として出る。
- `manon-jump-jhk-hoseigiri` は `damageOverride: 5272`。chain は 3,272 のセットアップ部分だけで、説明にある後続のコマ投げ／中段の読み合いは chain に含まれない。数値の算術的正否ではなく、**表示レシピの範囲と代表値の範囲が一致していない**ことが問題。

修正：`unknown / estimated / measured / calculated` 等の状態を値に付け、根拠・条件と一緒に一覧へ渡す。「確定部分」と「読み勝った場合」を分け、未確定値を既定のダメージ順で確定値と無条件に比較しない。`damageNote` の有無だけを信頼度にしない。

将来の計算処理は、ルートごとの合計を単純加算する責務と分ける。コンボ全体の順序、各入力の方法、開始条件、途中状態、ゲームバージョンを受け取り、各ヒットの内訳・適用条件・合計・計算不能理由を返す純粋関数にする案が適切。必要な入力項目と正解例は、オーナーの補正ロジック説明後に確定する。実測値による override には測定条件と理由を残す。

完了条件：未実測値だと一覧でも分かる。読み合い込みの数値を確定コンボの結果と誤認しない。補正式の完成は本項目の先行表示修正の必須条件にしない。

### R06 — ドラフト反映が途中成功になり、承認単位も曖昧

対象：[promote-draft](../scripts/promote-draft.ts) 35〜61 行付近、[check-drafts](../scripts/check-drafts.ts)。

promote はファイルを 1 件ずつ形だけ検証して直ちに rename する。後続ファイルで失敗すると、それ以前のファイルは本データに移動済みになる。参照先を含む全体検証は後回しで、既存ファイルとの競合処理も明示されていない。`drafts/*.json` 全件が対象なので、「今回承認したもの」と反映対象がずれる余地がある。

check-drafts は既存＋ドラフトを連結するため更新レコードを重複 ID と扱う一方、スキーマ・キャラクターまで含む統一された検証経路になっていない。Skill の標準手順にも接続されていない。

修正手順：

1. 対象ファイル／バッチを明示して読み込み、全件をスキーマ検証する。
2. ファイル名・内部 ID・character と出力パスの対応を確認し、既存との競合を事前に表示する。
3. 作成・更新を区別して ID 単位でマージした仮想データセットを作り、全参照・chain・表示用派生値を検証する。
4. dry-run で変更内容をレビュー可能にする。反映中に失敗しても元の状態へ戻せる方式にする。
5. プレビューも同じ仮想データセットから描画し、承認した対象だけを反映する。

完了条件：2 件目が不正でも本データと drafts が変更されない。無関係なドラフトを反映しない。既存 ID の更新を正しく検証できる。これは将来の仕様案であり、今回 promote 自体は実行していない。

### R07 — スキーマが形を検査しても、意味の違反が通る

対象：[スキーマ](../src/data/schema.ts)、[検証関数](../src/lib/graph/derive.ts)。

本データをコピーしたメモリ上の検査で、以下を確認した。

- マノンの route の `moveKey` をブランカの技に変更し、classic としても `validateAll` のエラーは空。技の存在だけでなく、参照元と参照先の character の一致が必要。
- Combo の `difficulty: 999`、`damageOverride: -100` が safeParse 成功。
- 未定義の `verified: true` を付けても safeParse 成功し、その項目は出力から削除される。AI がつもりで追加した項目が無視されても気づきにくい。

修正：難易度は整数 1〜5、ダメージは非負など、意味のある制約を追加する。キャラクター登録の存在と参照の一致、ID・パスの対応も確認する。ゲージの上限は回復等の仕様を踏まえて決め、単純に累積消費を 6 以下などと固定しない。管理下の JSON 入稿では未知フィールドをエラーにする strict スキーマも有効。

完了条件：上記不正例が、問題のレコード・フィールドを示して失敗する。未知の根拠情報を黙って落とさず、正式なメタデータへ取り込める。

### R08 — モバイルで「探す」「読む」までが遠い

対象：[BaseLayout](../src/layouts/BaseLayout.astro)、[ComboExplorer](../src/components/ComboExplorer.astro)、[コンボ詳細](../src/pages/[character]/combos/[slug].astro)。

390 × 844 px ではヘッダーが約 270 px、画面の約 32% を占有。マノン一覧の最初のカードはページ上端から約 1,364 px、確認した詳細のテキストレシピは約 1,692 px の位置だった。フィルターを使う前に候補を眺めたい人にも操作項目をすべて読ませる配置になっている。320 px ではマノン一覧の document 幅が 336 px となり横にはみ出した。

グラフには固定高さ 860 px が指定され、5 ノードの短いコンボにも大きな空白ができる。グラフ上のホイールでページスクロールが止まり拡縮されたことも確認。`touch-action: none` があるためタッチ時のページ移動との取り合いも実機で確認したい（実タッチ操作は未検証）。

画像：[モバイルの詳細](review-assets/2026-09-12/mobile-combo.png)、[短いコンボのグラフ](review-assets/2026-09-12/desktop-short-graph.png)。

修正案：

- モバイルのヘッダーは 1〜2 行程度に集約。表記・テーマ等は設定メニューへ置き、キャラクターとページ位置は見失わないようにする。
- 一覧は件数と基本フィルターを先に出し、詳細条件は折りたたむ。選択中条件はチップで常時確認できるようにする。
- タグと専用フィルターの重複を整理する。データ拡充後は技名・別名で探せる検索を追加すると有効。
- モバイルの詳細は短いレシピと主要条件を上に出す。グラフ高さは画面と内容に応じて制御し、拡大探索は明示操作で入る。
- 通常閲覧時は縦スクロールを優先するなど、グラフを操作する状態との境界を明確にする。

完了条件：320 / 390 px でページ全体が横にはみ出さない。基本候補やレシピを少ないスクロールで読める。グラフの上下へ移動する方法が分かる。縮小して文字を潰すだけの対応は避ける。

### R09 — 全画面と読みやすさのアクセシビリティ

対象：[FlowCanvas](../src/components/islands/FlowCanvas.tsx)、[共通スタイル](../src/styles/global.css)、[ComboExplorer](../src/components/ComboExplorer.astro)。

全画面は fixed overlay で、Tab を進めると背後の「テキストで見る」やリンクにフォーカスが移った。背景の overflow も visible。Escape 処理はあるが、モーダルとしてのフォーカス制御が不足する。

修正：全画面をモーダルとして扱うなら、`dialog.showModal()` または同等のアクセシブルな実装を使う。開いた時のフォーカス、背景の非操作化、閉じた際の元ボタンへの復帰、スクロール制御を確認する。[WAI-ARIA の Dialog 指針](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)、[HTML dialog の手法](https://www.w3.org/WAI/WCAG22/Techniques/html/H102)を参照。

ブラウザーの計算済み文字色と背景色から求めた比率は以下。通常サイズの文字で 4.5:1 を必要とする基準に届かない箇所がある。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)の Contrast (Minimum) を参照。装飾用の未点灯の星は、この表の問題件数に含めていない。

| テーマ・対象 | 文字サイズ | コントラスト比 |
| --- | --- | --- |
| Dark：フィルター見出し | 約 12.5 px | 3.56:1 |
| Dark：ダメージ注記 | 約 11.5 px | 3.56:1 |
| Dark：件数 | 約 12.8 px | 4.20:1 |
| Light：ページ h1 | 16 px・通常太さ | 3.70:1 |
| Light：件数 | 約 12.8 px | 4.18:1 |

ピクセル表現をブランド要素として残し、本文・補足は読みやすい書体と大きさにする。h1 が 16 px・通常太さのため、ページ名と操作項目の階層も弱い。見出しの大きさ・余白を明示的に定義する。

あわせて、フィルター群の fieldset / legend、ソートの label、件数の更新通知、拡縮ボタンの accessible name、操作方式切替の選択状態を確認する。タッチ向け操作部は 40〜44 px 程度を設計目安にできるが、これは WCAG AA の最小値そのものではない。[Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) は原則 24 × 24 CSS px と間隔等の例外を含む。

完了条件：全画面をキーボードだけで開閉でき、背後へフォーカスが抜けず、元の操作位置へ戻る。両テーマで必要な文字のコントラストを満たす。

### R10 — モダン切替がグラフ内だけに閉じている

対象：[FlowCanvas](../src/components/islands/FlowCanvas.tsx)、[コンボ詳細](../src/pages/[character]/combos/[slug].astro) の `text-recipe`。

`/blanka/combos/blanka-antiair-5mk-electric/` でモダンにするとグラフは切り替わるが、外側のテキストレシピはクラシック表示のまま。`data-control` がグラフの `.fc` にだけ付く構造による。

修正：入力方式の選択をページ共通の状態へ引き上げ、テキストと図を同期する。入力方式（Classic / Modern）と見た目（アイコン / テキスト）は別軸として扱う。図を使いづらい人がテキストを代替表示にできることを保証する。

なお、この例はグラフで最初と次の技がともに `5中`、クラシック側では `4中K` → `5中K` と出る。ゲーム上のモダン操作の正誤は未判定だが、辞典の代表入力で各 Step の方向・状況を失わないか、R01 の resolver と実機確認で扱うべき具体例になる。

完了条件：両対応コンボを切り替えた際、図・テキスト・表示中の入力方式が一致する。

### R11 — 戻る操作でソートの既定値を復元しない

対象：[ComboExplorer](../src/components/ComboExplorer.astro) の `readURL()`、`writeURL()`。

再現：マノン一覧の既定状態 → セットプレイタブ → コンボタブ → 難易度昇順を選択 → ブラウザーで戻る。戻り先の URL に sort がなくても難易度昇順が残り、`?sort=diff-asc#setplay` に書き換わる。`readURL()` が sort のある時だけ select を設定しているため。

修正：省略時は明示的に `damage` に戻す。不正な sort 値も既定値へ正規化する。URL を読み込む処理と、操作結果を書き込む処理を分離し、popstate 時に意図せず履歴を書き換えない。

完了条件：sort あり／なし、不正値、タブ移動を含む戻る・進むで URL と UI が一致する。

### R12 — テスト、Skill、公開ゲートを同じ仕様にそろえる

対象：[graph.test](../tests/graph.test.ts)、[登録 Skill](../.claude/skills/register-combo/SKILL.md)、[package.json](../package.json)、[ROADMAP](ROADMAP.md)、[README](../README.md)。

**テストの問題：**「合計ダメージはパーツ damage の和」というテストは、実際には step 数と totalDamage が正かだけを調べ、和への一致を検査しない。totalDamage が誤って 1 になっても通る。既存 fixture 中心のテストでは、新データの `inputModernPrecise` や `feint` が表示まで正しく通ることも保証できていない。57 件の成功は有益だが、意味の保証範囲を正しく捉える必要がある。

修正：テスト名の性質を直接 assert する。R01〜R04 の実際の不具合を落とすケースを追加し、実データを読み込んだ派生値の検証も用意する。将来のダメージテストはオーナー提供の正解例を固定し、実装自身から期待値を作らない。

**Skill とプレビューの問題：** マノン固定の参照パスと `/manon/_preview/` が残るが、実装のページは `/preview/`。プレビューは主に JSON と単体検証で、Skill がいうレシピ・分岐等の表示確認を十分に実現していない。複数キャラ対応、既存レコード更新、全体検証、起動手順を現実に合わせる。リポジトリ指定のバックグラウンド起動方針ともそろえる。

Skill には不明値を null とする方針がある一方、Route の damage や resource は数値必須。AI に推測値で埋めさせないため、不明を表現するモデルと表示を先に整える。推測の文章を正式データの根拠扱いしない。

**公開ゲートの問題：** `deploy` は build → deploy で、check を必須にしない。ビルド時のデータ検証はよいが、テスト・型検査の代わりにはならない。文書の Workers Builds 手順も build 中心。PR または公開ジョブに `npm ci` → `npm run check` → `npm run build` を必須化し、通ったコミットを公開対象にする。公開後はトップ、キャラ、代表コンボ、404、サイトマップを小さく検証する。

**ドキュメントの問題：** README が Astro starter のまま、ROADMAP に旧ページ数・旧 preview パス・進捗の混在が残る。SPEC は仕様、ROADMAP は未完タスク、CONTENT は入稿ルール、Skill は実行手順として役割を決め、同じルールを何箇所にも書き直さない。

完了条件：新規キャラクターのドラフトを作り、正しい URL で本番と同じ表示を確認し、指定した変更だけを反映できる。既知の不具合を戻すとテストが失敗する。公開処理が必須検査を迂回しない。

## 4. その他の改善と、急いで変更しなくてよいもの

### 公開状態・静的出力

公開トップでは「Phase 1」「全件ダミー」の説明が残る一方、フッターは Phase 2・実データ投入中。ローカルではトップの古い説明は既に除去されているため、再修正の前に公開対象を確認する。[確認時の公開画面](review-assets/2026-09-12/public-home.png)。

ローカルの production build には `dist/preview/index.html` が存在する。内容は 404 表示だが、単純な静的配信では HTTP 200 になった。`new Response(..., {status: 404})` と静的成果物の生成・配信の関係を確認し、dev 専用ページを本番の成果物から除外するのが明確。確認時の公開 `/preview/` は 404 で、ドラフトが公開されていることは確認していない。[Astro の routing](https://docs.astro.build/en/guides/routing/)を参照。

### 性能・リファクタリング

現時点で Astro を全面的な SPA に置き換える理由はない。本文の静的配信とグラフへの Preact 導入は合理的。[Astro の framework components](https://docs.astro.build/en/guides/framework-components/)が説明する部分的な対話機能の使い方と整合する。

今回、最大の生成 HTML はマノン一覧の約 165 KB、FlowCanvas の JS は約 22 KB、dagre を含む共有チャンクは約 47 KB（いずれも非圧縮）。全体の配信量や実端末の速度を示す指標ではないが、今すぐ構成を変えるほどの性能劣化は確認していない。

先に整理するなら次の順番がよい。

1. R01/R02 の共通の表示モデルと辞書。正しさに直接効く重複をなくす。
2. FlowCanvas のレイアウト計算、パン・ズーム操作、表示部品を分け、各変更の影響範囲を狭める。
3. `src/data/index.ts` と `content.config.ts` の二重のデータ読み込み方針を整理する。同じ正規化・検証を使い、どちらが正本か明示する。[Content collections](https://docs.astro.build/en/guides/content-collections/)を参照。
4. 必要になった段階で ID・入出辺の索引や、一覧での重複 flatten を整理する。現在の規模では主にビルド時の処理であり、これだけを利用者の速度問題と断定しない。

コマンド DSL では `DI` が専用の意味を持つトークンではなく `D` と `I` の文字として残る例もあった。表記ガイドが扱う語彙と parser の対応表をそろえ、未知トークンを無言で通す範囲を決めたい。

## 5. 開発タスクの組み直し案

現在はデータ追加と機能拡張が進み、旧ロードマップ上の完了と実データでの品質がずれ始めている。日付だけで完了を判定せず、次の順番と受入条件で再整理することを推奨する。

| 順序 | 作業単位 | 対象 | 終了条件 |
| --- | --- | --- | --- |
| 1 | 入力・レシピの信頼性 | R01、R02、R10 | 同一コンボがどの表示でも同じ操作内容になる |
| 2 | 状況と数値の意味 | R03、R04、R05 の表示部分 | 入口から対象を見つけられ、確定／未確認／読み合いが区別できる |
| 3 | 入稿と検証の仕組み | R06、R07、R12 | 不正・未承認のデータを途中反映しない。実例の回帰を検出する |
| 4 | モバイルとアクセシビリティ | R08、R09、R11 | 狭幅・キーボード・戻る操作の受入条件を満たす |

## 6. AI と一緒に開発するための具体策

AI に「全体をきれいにして」と依頼するより、**不具合の実例 → 期待される意味 → 変更範囲 → 完了条件**を渡す方が今回の問題に効く。

- 各変更の前に、入力 JSON が検証・派生値・画面へ渡る経路を短く書かせる。新フィールドを schema に追加しただけで完了にしない。
- データの正しさは、情報源・対象ゲームバージョン・確認条件・確認者・状態で管理する。AI 自身の説明文を検証済みの根拠にしない。
- 「不明」は正式な状態として扱う。未確認のダメージ、フレーム、モダン対応を埋めるための推測を要求しない。
- バグ修正では修正前に落ちるテストを選ぶ。単に値が存在する・例外がない・スクリーンショットが生成できる、だけで仕様が正しいとしない。
- 小さな画面確認セットを用意する。代表的な両対応、classic 専用、精密入力のみ、空振り／フェイント、起き攻め分岐を含め、モバイル・ライト・キーボード操作を回す。
- 開発ルールは AGENTS / CLAUDE に簡潔に置き、詳細仕様は docs へリンクする。新キャラ対応等で Skill の手順も変更対象に入れる。
- PR の説明には「何が誤っていたか」「利用者から見た変化」「実行した検査」「未確認のゲーム条件」を書く。AI が「完了」と言うことと受入条件を満たすことを分ける。

Claude へ渡す依頼文の例：

> docs/REVIEW-2026-09-12.md の R01 と R10 を対応してください。最初に現在の入力解決と表示状態の流れを確認し、精密入力だけがある実データで失敗するテストを追加してください。可否と表示コマンドの resolver を統一し、グラフとテキストを同期してください。ダメージ補正式はオーナーから後日説明予定なので推測で実装しないでください。npm run check と npm run build を実行し、該当コンボの両入力方式をブラウザーで確認してください。結果と残る未確認事項を報告し、この作業ではデプロイしないでください。

残るゲーム固有の確認事項は、フレーム・受け身・択の勝敗条件、通常技の入力方向とモダン辞典の関係、補正切り後の追撃の成立条件。コード検査だけでこれらを実測済みとは扱わず、オーナーの知識・根拠資料・トレーニングモードの確認を必要な箇所に絞って依頼するとよい。
