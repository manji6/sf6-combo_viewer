# ダメージ計算：実装前の設計評価・調査メモ

作成日：2026-09-12。対象：現在のマノン／ブランカのデータモデルと ROADMAP §7。

追加ネット調査：[DAMAGE-CALCULATION-RESEARCH-2026-09-12.md](DAMAGE-CALCULATION-RESEARCH-2026-09-12.md)。一般ルールの候補、入力補正の例外、丸めの比較例、残る確認を収録。以下の未決事項は「全て未調査」という意味ではなく、対象版での採用を確定していない項目。

**提案段階。ゲームの計算式は未確定で、オーナーから補足を受ける予定。** この資料は計算器の実装ではなく、Claude が実装を始める前に必要な設計・情報・検証を整理したもの。採用した仕様は SPEC、入稿ルールは CONTENT と登録 Skill に反映する。

## 1. 評価：先に設計を追加する必要がある

技の基礎ダメージと補正をデータ化する方針はよい。ただし、技辞典だけから常に正しい合計を出せるわけではない。同じ技でも、当て方、入力方法、開始状態、途中の状態変化、前後の技との関係によって計算条件が変わる。Route の単体ダメージを足す構造では、それらを引き継げない。

以下は現在のコード・データから確認できる不足であり、ゲーム仕様の推測ではない。

| 現状 | 計算機能に追加で必要なもの |
|---|---|
| `flattenCombo` は `Route.damage` を合算し `damageOverride` を優先 | コンボ全体を順に処理する計算器。Route 分割によって計算が変わらないこと |
| `Move.damage` は単一の数値または null | 強度・条件別の基礎値、必要なケースのヒット別配分。null と真の 0 の区別 |
| `comboScaling` は文章 | 数値の意味、発動条件、適用対象、適用タイミングを分けたルール |
| `Step.cancel` は boolean、条件は command / note にも入る | 必要なケースではキャンセル元・種別・接続を構造化。コマンド文字列から計算条件を推測しない |
| `inputModern` と `inputModernPrecise` は表示用文字列 | 実際に選択した入力方法と技のバリアント。モダン全体への一括倍率では表現不足 |
| `whiff` / `feint` にも moveKey が付く | 技の使用とヒット発生を分離。空振りの技をダメージとして数えない |
| マノンのメダル条件は notes、SA3 にキャンセル条件の文章 | 開始メダル、途中の獲得タイミング、技別・接続別の評価条件 |
| ブランカの SA2 / 爆弾設置は damage 0 | 状態変化／設置／着弾を別イベントにする。0 だから何もしない処理にしない |
| 補正切りの後続を同じ chain に含めるケースがある | 確定コンボごとの区間、読み合いを経た接続、区間別の結果 |
| `verifiedVersion` に「Year3・パッチ版数未確認」が入る | 計算ルールと技データの対象版、確認状態、測定条件 |

参照：[スキーマ](../src/data/schema.ts)、[集計処理](../src/lib/graph/derive.ts)、[マノン SA3](../src/content/moves/manon/manon-sa3.json)、[ブランカ SA2](../src/content/moves/blanka/blanka-sa2.json)、[爆弾設置](../src/content/moves/blanka/blanka-bomb-l.json)。既存 JSON の説明がゲーム内で正しいかは別途検証する。

## 3. 式を書く前に決めるルール表

下表は **確認項目**。現行版のゲーム仕様として確定した表ではない。各行に `ruleId / 値・単位 / 条件 / 適用時点 / 対象版 / 出典 / 実測例ID` を付ける。

| 項目 | 確定すべき内容 | 区別する実例 |
|---|---|---|
| 基本補正 | 何を一段と数えるか。同じ技の再使用、多段、派生、ターゲットコンボの扱い | 同じ通常技を 2 回、多段技 1 回、派生を追加 |
| 始動補正 | 初段自身と後続のどこへ掛かるか。通常の進行と置換／加算の関係 | 同じ技を初段／途中に置く |
| 追加コンボ補正 | 公式等の数値が基本分込みか、追加分だけか | 追加補正技を挟む／挟まない |
| 即時補正 | 当該技・後続への適用、単発時の扱い、キャンセル元条件 | 単発 SA、通常キャンセル、指定技からのキャンセル |
| DR | コンボ前とコンボ中、発動時と次の着弾時、複数回発動の扱い | 生ラッシュ始動、CDR、コンボ中に 2 回 |
| ジャストパリィ・DI | 反撃成立条件、DI ヒット／ガード壁やられ／スタンの違い | 同じ追撃を各開始条件で測る |
| Counter / Punish Counter | 当該ヒットの基礎値変更か補正率変更か。技ごとの例外 | 通常技、投げ、SA、多段技で比較 |
| モダン | 簡易／手動／アシストの区別、各技への適用、元データに倍率込みか | 同じ技・同じ条件で入力方法だけ変える |
| モダン補正の継承 | 派生元の入力方法、一部 SA 後の持続、次の簡易入力との重複適用 | マノンの派生、ブランカ SA1 後の爆弾、SA2 発動を比較 |
| 最低保証 | 通常の下限、技別 SA / CA の保証、乗算との前後関係 | 複数補正が重なる SA、保証の直前／直後 |
| 丸め | 補正率・各ヒット・合計のどこで切り捨て等を行うか | 端数が出る基礎値、多段、DR＋入力補正 |
| 状態変化 | メダルを読む／増やす順序、SA2 発動の効果と適用時点 | 状態変化の直前／直後にダメージがある例 |
| 区間終了 | 何をもって連続ヒット終了とするか。終了後も持続する状態 | 空振りを挟んでも継続する例、実際に切れる例 |
| 遅延ヒット | 技の使用回を数える時点、着弾順、他技が割り込む場合 | 設置→別技→着弾、部分ヒット、同時着弾 |

「20%補正」だけのフィールド名は避ける。20 ポイント減算なのか、残存率 0.8 なのか、倍率 0.2 なのかを型・単位で区別する。記事の一般式だけで、技別の条件付きルールを上書きしない。

## 4. 初期の対象範囲

最初は **通常の対戦ルールにおける、成立確認済みの直列コンボの体力ダメージ**を対象にする案を推奨する。

- 対応ルールがそろったマノンの少数コンボから始める。キャラクター全技への一括対応を前提にしない。
- 計算条件として通常／特殊始動、入力方法、必要なキャラ状態を指定する。条件未指定を都合のよい値で埋めない。
- コンボがつながるかの判定、フレームシミュレーション、最適コンボ探索は対象外。計算値が出ても「成立確認済み」にはしない。
- ガード削り、回復可能ダメージ、相手の残り体力で打ち切るリーサル計算、ドライブ・SA ゲージの増減、アバター対戦は別機能として範囲を決める。
- ブランカの発動・設置・遅延ヒットはモデルの拡張先を確保するが、初期から全挙動を実装しない。未対応なら理由を返す。

初期に除外したケースも既存サイトから消す必要はない。条件の合う実測値があれば表示し、それ以外は未計算または目安とする。

## 5. データと計算処理の設計案

### 5.1 責務と処理の流れ

```text
Combo + Route + Step + Move + 入力条件
  → 検証・バリアント解決
  → 計算用イベント列（由来の routeId / stepIndex を保持）
  → バージョンを指定したダメージ計算器
  → ヒット／区間の内訳・合計・不足理由
  → 実測記録との比較
  → 一覧・詳細・プレビュー共通の表示モデル
```

`src/lib/damage/` に DOM・Astro・グローバルのデータ読み込みに依存しない純粋関数を置く案。辞典とルールは引数で注入する。`flattenCombo` にゲーム固有の条件分岐を集中させず、返された結果を表示用にまとめる。

### 5.2 データを置く場所

| 層 | 保持する情報の案 |
|---|---|
| ルールセット | ゲーム対象版、アルゴリズム版、補正進行、適用順序、丸め・最低保証の方針、検証状況 |
| Move の計算プロファイル | 技バリアント、基礎値、必要なら hit 配分、補正条件・イベント、必要状態、根拠 |
| Step / 計算レシピ | 実際の入力方法、技の使用回、hit / whiff / block 等の結果、当たった部分、接続条件 |
| コンボの開始条件 | 通常／特殊開始、既存コンボの途中か、新規開始か、メダル・強化状態等 |
| 区間と境界 | 確定コンボの区間 ID、次区間への読み合い、引き継ぐ状態 |
| 実測記録 | 測定値、条件、対象版、ヒット内訳、確認日、証拠、確認状態 |

フィールド名・配置は仮案。表示用の既存 Step を壊すより、初期は明示的な計算メタデータを足し、そこからイベント列を生成するのが移行しやすい。単純な直列コンボには人間が全イベントを二重入力しない仕組みにする。例外だけ明示列を必要とする設計がよい。

`comboScaling` の文章を実行時に自然言語解析して計算しない。移行時に元文と根拠を残し、確認したルールへ手動またはレビュー付きで変換する。

### 5.3 使用回・ヒット・状態変化を分ける

同じ `moveKey` を二度使った場合を識別できる `actionInstanceId` を持つ。ひとつの使用回に複数の `hitId` が属する。補正上の数え方が技の使用回と異なる場合は、技プロファイルでその関係を定義する。**moveKey のユニーク数、Step 数、hit 数のどれか一つを無条件に段数としない。**

候補となるイベントは `hit`、`driveRush`、`stateChange`、`segmentEnd`、設置物の生成／着弾など。イベント名はゲーム挙動を確定した後に絞る。空振りはダメージイベントを発生させなくても、状態変更等があればそのイベントを残す。

追加調査で入力補正の派生・後続への継承が報告されているため、親の操作ID、補正の適用範囲、適用開始イベント、重複を管理する識別子も持てるようにする。`inputMethod === modern` のような一律分岐で倍率を決めない。通常ルールと技別条件の加算／置換を区別し、同じ補正を二重に掛けない。

初期の直列処理ではフレーム単位のシミュレーターは不要。遅延ヒットがある時は、ユーザーが確認した着弾順を計算列に持たせる。同時着弾など順序未確定のケースは勝手に並べず未対応とする。

### 5.4 補正切りと共有パーツ

Route 境界は再利用上の区切りなので、計算状態は引き継ぐ。同じ Route でも前段の履歴が違えば結果は変わり得る。Route 単体の結果を routeId だけでキャッシュしない。

逆に、同じ routeChain 内でも確定コンボが切れるなら区間を分ける。空振り・フェイントの存在だけで自動判定しない。コンボ固有の補正状態を初期化しても、メダルや強化状態等をすべて初期化してはいけない。何を引き継ぐかはルールセットで決める。

結果は「確定部分」「次の読み合いに勝った部分」を区別する。必要なら条件付き総量も出せるが、確定コンボの合計とは別の表示・ソートにする。

### 5.5 結果の契約

概念的には次の区別を持たせる。これは API 確定コードではない。

```ts
type CalculationResult =
  | {
      status: 'calculated';
      segments: SegmentBreakdown[];
      context: ResolvedContext;
      rulesetId: string;
      algorithmVersion: string;
      dataRevision: string;
    }
  | {
      status: 'incomplete' | 'unsupported';
      reasons: CalculationIssue[];
      partialBreakdown?: HitBreakdown[];
    };
```

各 hit の内訳には、基礎値、適用ルール ID、補正前後の値、丸め・保証値の適用、最終ダメージ、前後状態、元の Step を保持する。これにより「合計が 20 違う」時に最初の不一致から調べられる。

`calculated` は「入力したモデルで計算が完了した」の意味。ゲーム内で検証済みという意味ではない。実測との一致状態を別に保持する。情報不足の途中合計を最終合計として返さない。

倍率の演算には整数・固定小数等を検討し、丸めの位置を一箇所の明確なルールにする。ただし「最後に floor すればよい」とはまだ決めない。DC-1 の正解例で判定する。

## 6. 既存データと UI の移行

1. **現行値の保全**：`Route.damage` と `damageOverride` を消さず、legacy の目安／実測根拠未確認として出自を棚卸しする。既存 override を一律に実測済みへ昇格させない。
2. **条件付きの観測値**：実測は `observations[]` 等へ移す案。開始メダル、入力方法、対象版が計算条件と一致した時だけ比較する。
3. **並行計算**：選んだ少数コンボで既存表示と新計算を比較する監査出力を用意する。全件をいきなり置き換えない。
4. **表示統合**：計算値、条件付き実測値、目安、未計算を同じ表示モデルへ解決する。値の選択理由を内部に残し、実測との不一致を override で隠さない。
5. **一覧の条件**：代表条件を明示する。詳細でメダルや入力を変えた値と一覧の既定値を混同しない。モダン可否・アイコン表示の切替だけで倍率を決めない。
6. **ソート**：同じ条件・区間の値を比較する。未計算を 0 にせず、別枠か末尾。異なる実測条件を混ぜた順位にしない。
7. **Skill 統合**：必要な技プロファイルや条件がない時は不足項目を列挙する。ダメージを推測で埋めて promote しない。

**既存文書との衝突に注意：** CONTENT §6.1 は「実測・素点合計などの制作メモを JSON に残さない」という運用を含む。一方、計算器の検証には非公開の根拠・測定記録が必要。公開表示用の短い状態ラベルと、編集者向けの証拠・検証メタデータを分ける方針へ見直す。公開成果物に編集メタデータが不要なら出力時に除外する。今回この運用方針を無断で確定仕様へ書き換えてはいない。

## 7. テストと受入条件

### 正解例の記録テンプレート

```text
caseId / 対象ゲーム版 / キャラクター
技バリアントと使用回順 / 実際の着弾順 / 当たった hit
各技の入力方法 / 通常・CH・PC 等の条件
開始メダル・強化状態 / DR や状態変化の時点
確定コンボの終了位置 / 読み合い後の次区間
各ヒットの表示ダメージ・補正率 / 区間合計
測定日 / 確認者 / 動画等の根拠 / 不明点
```

最初の目安は 10〜15 例。ただし件数だけで完了にせず、採用するルールの分岐を網羅する。現行 JSON の値をそのまま正解にせず、オーナーの説明と対象版の実測値を固定した fixture にする。

| テスト群 | 確認すること |
|---|---|
| 単発・基本進行 | 同じ技の再使用、多段、初段／途中で同じ技 |
| 特殊補正 | 始動・追加・即時をそれぞれ単独と組合せで検証 |
| DR | 生ラッシュ始動、コンボ中、複数回。発動イベントの位置 |
| 入力方法 | Classic／Modern 手動／簡易のうち対応するもの。混在コンボ |
| SA / CA | 単発、途中、条件付きキャンセル、保証値の境界 |
| 端数 | 基礎値への直接乗算と補正率丸めで結果が分かれる例 |
| 状態依存 | メダル開始条件、途中獲得、ブランカ発動前後 |
| 非ヒット | whiff / feint / 設置。0 と unknown の区別 |
| 区間 | 同じヒット列の Route 分割では結果不変。実際の補正切りでは区間別結果 |
| 未対応 | データ不足、着弾順不明、対象版不一致を正常値に見せない |
| 表示 | 同じ入力条件で一覧・詳細・プレビューの値と状態が一致 |

機械的な性質のテストも有効：同じ入力なら同じ結果、hit 内訳と区間合計の一致、データを変更しない純粋性、ダメージ以外に作用しない待機を挿入しても値が不変、入力エラーが元の Step を指すこと。ゲーム上の状態効果を持つ行動まで「挿入しても不変」としない。

受入条件：対応範囲では各ヒットと合計が正解例に一致し、不一致の箇所を説明できる。未対応では理由を表示する。対象版を変更した際に影響する技・Route・Combo と実測例を再確認できる。check / build を通し、表示例をブラウザーで確認する。

## 8. オーナーの補足時に優先して確認すること

1. **対象ゲーム版と最初の範囲**：最初に自動計算したいコンボを具体的に選ぶ。全マノン／全ブランカ対応を一括で約束しない。
2. **計算順と丸め**：始動・追加・即時・乗算・最低保証の順序を、途中値が分かる例で説明してもらう。
3. **条件の扱い**：通常／CH／PC、DI の状態、ジャストパリィ、入力方式、キャンセル元について、最初にどこまで扱うか。
4. **固有技の例外**：マノン SA3 の既存キャンセル条件、メダル更新の時点、ブランカ SA2・設置ヒットの正解例。
5. **既存値の出自**：どの override が、どの条件で測定されたものか。判明しない値は未確認のまま保つ。

この回答を待つ間も、結果型の設計、未知値の表示、入力 resolver の整合、実測記録のテンプレート整備は進められる。正式な補正式の実装・公開は、採用範囲のルールと正解例がそろってから進める。
