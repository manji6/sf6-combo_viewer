## 4. 進め方の妥当性レビュー（自己評価）

### 妥当だと考える点

- **2フェーズ制（ダミーで UI 確定 → 本開発）は正解**。実際、フローグラフ表示・起き攻めの特徴表示・クラシック/モダンの扱いで
  データモデルへのフィードバックが多数出た（moves 辞典・wakeup 構造化）。先に全データを入れていたら手戻りが大きかった。
- **schema を Phase 1 のうちに固めた**（A-1〜A-4）のは前倒しとして妥当。Zod 化（P2-1）と大量データ投入（P2-7）の前に
  型が安定しているほど手戻りが減る。
- **3層グラフ ＋ 技辞典**の構造は、共有パーツ（起き攻めと頻出コンボの連結）という当初の狙いを満たしつつ、
  フレームデータの重複を避けられている。
- Content Collections への移行は**構造を変えず TS 配列 → JSON にするだけ**なので低リスク。

### 調整を推奨する点

1. **Phase 1 を「正式にクローズ」する区切りを設ける。**
   いま UI/UX レビューとスキーマ作業が混ざっている。§1-A の3項目に結論を出し、§1-B を一巡修正したら
   「Phase 1 完了」と宣言してから Phase 2 に入る。これは元計画のゲートそのもの。

2. **Cloudflare Pages 連携（C-1.5）を Phase 2 の最後ではなく今やる。**
   GitHub 連携は済んだので設定 5 分。共有 URL があれば localhost 往復なしでレビューでき、
   以降 `main` push のたびに最新が見える。本番ドメイン割当（C-3）だけ後回しにすればよい。

3. **Phase 2 に「実データの最小シード（P2-4）」を明示的に挟む。**
   元計画は「スキーマ確定 → 検証 → SEO → Skill → 実データ」の順だが、Skill を作る前に
   マノンの実コンボを 5〜10 本手で入れて**スキーマを現実で殴っておく**。ここで型の不足が分かったら
   P2-1 に戻る方が、Skill を作り込んでから直すより安い。

4. **SEO（P2-8）とテスト（P2-9）は本流と並行できる。**
   P2-2 が済めば SEO は独立して進められる。テストは P2-1 の型が決まればいつでも。
   直列に積まず、実データ投入（時間がかかる）の裏で進める。

5. **`register-combo` Skill は「作り込みすぎない」。**
   最初は「numpad 正規化 ＋ 既存ノード再利用の提案 ＋ プレビュー ＋ 承認後書き込み」まで。
   YouTube 字幕解析などは後で足す。P2-6 を重くすると実データ投入が遅れる。

### 想定リスク

| リスク | 対応 |
|---|---|
| `moves` の実データが膨大でオーナー作業が詰まる | まずダミー登場分＋主要技だけ。全技は「あれば出す」程度に段階投入 |
| ノード粒度の運用（U-6）が実データで破綻 | `CONTENT.md`（P2-5）で基準を明文化。破綻したら「補正別ノード」等の例外を追加 |
| フレームデータの著作権（Capcom IP） | 非商用ファンツールのグレー領域（dustloop 等と同じ扱い）。出典明記・広告なしを維持 |
| Cloudflare Pages のビルドが Windows ローカルと差異 | `npm run build` が CI でも通るか C-1.5 直後に確認。Node バージョンを固定 |
